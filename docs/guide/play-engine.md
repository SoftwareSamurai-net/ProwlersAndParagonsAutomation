# The play engine

Read before touching `play/` — the second engine, which resolves an action where `engine/` costs and validates a character.

> Part of the guide set indexed by [`CLAUDE.md`](../../CLAUDE.md). Read that first; it carries the
> disciplines that apply whatever you are working on. **Open work lives in
> [`PROGRESS.md`](../../PROGRESS.md)** — this file records how things are, not what is left.

Read [`play-rules.md`](play-rules.md) too: it is the store this engine reads, and every convention it records — `interpretation` against `ambiguity`, `table_setting`, `transcribed_here: false` — decides what this engine is allowed to do with a field.

## What `play/` is, and what it is not

`play/` is a project beside `engine/`. It references `engine/` and **nothing on the character side references it back** — not `engine/`, not `sheets/`, not `cli/`, `web/` or `mcp/`. Exactly two projects do: the test project, and `mcp-play/`, the encounter server that is this engine's one host (see [`mcp-and-headless.md`](mcp-and-headless.md)). `PlayContractTests` holds that list as an allowlist, so a third reference is flagged rather than missed.

| It is | It is not |
|---|---|
| the authority on **what happens** when somebody attacks, moves, grapples or spends Resolve | the authority on what anything **costs** — `CostCalculator` is, and `play/` may not name it |
| a reader of `data/rules/play/` | a reader of `data/rules/*.json`; it holds no opinion about Powers, Pros or Hero Points |
| a pure function over an immutable state | a simulation loop that mutates a `CharacterSheet` — it cannot reach one after `CombatantFactory` |
| told what kind of combatant it is looking at | allowed to read the character's palette flag to work it out |

`CLAUDE.md`'s settled list is where this comes from, in one line: **play rules do not go into `engine/`, which is the authority on cost and validity and knows nothing about resolving an action.** A combat simulator is a *second* engine beside it.

**Four guards hold that, and three of them were already here.** `play/` is on `AccountsContractTests`'s and `PresentationFlagsTests`'s list of rules projects, so it inherits *no account*, *no filesystem*, *no network* and *no presentation flag*. `PlayContractTests` adds the two that are new: `engine/` and `sheets/` never name `play/` in either spelling, and `play/` names neither `CostCalculator` nor `CharacterValidator`. Every one carries a positive control that the names it scans for are real, because a scan for names that no longer exist passes on everything.

## Reading the rules: `PlayRulesRepository`

Same shape as `RulesRepository` and none of its data. Five files, lazy, snake_case, read through the same **synchronous** `IRulesSource` — a host that can only load asynchronously does it once and hands over strings, exactly as the browser already does for the character rules.

**`PlayRulesRepository.DataFileNames` and `RulesRepository.DataFileNames` never meet, and a test says so.** That second list is what a browser fetches at boot; a play file on it is a public URL nobody asked for, which is the same exposure `PlayPayloadTests` keeps the csproj globs away from, reached by another route.

**A lookup that misses is a throw, not a null.** Every read here is a rule the engine is about to apply, and a rule that resolved to nothing would produce a plausible number with no rule behind it.

**The models cover every key of every entry**, because `PlayRulesFileCoverageTests` re-reads the five files with `JsonUnmappedMemberHandling.Disallow` — the shape `RulesFileCoverageTests` already uses, and for the failure it was written for: `creation_rules.json` carried five keys nothing read, and one of them had rotted away from the engine while reading as a source of truth. The repository itself stays lenient, so a data edit is a failing test rather than a broken host. That check earned its keep on the day it landed: the merge from the Chapter 4 branch renamed four fields and it caught all four.

**Prose, `ambiguity` and `interpretation` are modelled too.** They are part of the file and a reader of an entry needs the ambiguity beside the number. What the engine may *consume* is narrower — see below.

## The dice contract

```csharp
public interface IDiceSource { int[] Roll(int count); }
```

**It returns raw d6 faces, and that is the whole of the design decision.** A source that answered with a count of successes would be smaller and would be wrong, because three printed rules change the *mapping* rather than the pool:

- **Checking Your Swing** (Ch.3 p.69) flattens a six from two successes to one.
- **The sub-1d floor** (p.67) throws one die that scores only on a six, and only for one.
- **Every exploding-six offer** in the book — the Defining Moment's, the team attack's, Checking Your Swing's paid one — rerolls a *face*.

None of those survives the faces being thrown away. `PROGRESS.md` item 14 records the same reasoning as a decision taken before the slice started.

Two implementations ship:

- **`SeededDice(int seed)`** — deterministic, and it keeps its `Seed` as a property so a report can print it. A balance figure without its seed is a figure nobody can reproduce.
- **`ScriptedDice(params int[] faces)`** — the faces a printed example rolled, in order. **It throws when it runs out**, which is a positive control rather than defensive programming: a source that quietly returned zeros would let an engine that skipped a defence roll still reach the printed answer. `Remaining` is the other half — a fixture asserts it is zero at the end, which catches an engine making *more* rolls than the page.

`SuccessCounter` is where faces become successes, and **there is no literal 2, 4 or 6 in it**. The map, the sub-1d floor and the automatic-success rate are all `play_meta.json`'s; Checking Your Swing swaps the map for `challenge.json`'s rather than correcting the answer afterwards.

## The ledger

Every rule the engine applies writes a `LedgerLine` naming the entry's id and carrying its `source_ref`, so **any figure in a run traces to a printed page**. That is not decoration: the owner wants balance measured rather than guessed, and a measurement is worth what its audit trail is worth.

Three things the ledger is deliberately used for beyond narration:

- **A table setting that is on says so on page one**, and one that is on but *not yet applied* says that instead. A setting accepted and quietly ignored is the worst of the three possible behaviours — the report prints the setting, the numbers do not carry it, and nothing says so.
- **An unimplemented intent says `not yet implemented`, by name, and changes nothing else.** A silent no-op is indistinguishable from a rule that ran and had no effect, and a balance measurement turns on exactly that difference.
- **Where the engine follows an `interpretation`, the line says so and quotes the printed word it is departing from.** A reading applied silently is a reading nobody can argue with.

## The fixtures rule

> **A mechanic is proved by a printed example or by a property, never by a test that restates the code.**

Two transcriptions can agree and both be wrong — which is why `data/rules/play/` is held to the book by a reflection walk against `CanonicalCombatRules` and its siblings rather than by a second copy of itself. An engine checked against a test somebody wrote from the same reading of the page is a *third* transcription carrying the same defect. The authors' own arithmetic cannot be talked round.

`PlayWorkedExamples` holds the eight the book prints — p.67's arm wrestling, p.74's movement and chase, p.76's Mind Control and the escape from it, p.79's Clint Castle, p.81's whole fight, p.85's Adversity. **They return verdicts rather than asserting**, because they are driven twice (below), and a twin with a doctored harness proves nothing.

**Every example carries a positive control before its outcome.** The book prints *successes* and `IDiceSource` returns *faces*, so each scripts faces chosen to produce the printed counts and then requires the engine to have counted exactly those — the count first, the consequence second. Three of this repository's four historical guard faults were a feature that did not run being mistaken for a feature that worked.

`PlayEnginePropertyTests` holds what no worked example can: a run always terminates inside its page limit, Health never falls below the entry's own defeat floor while Fatal Damage is off, a step never modifies the state it was given (compared by serialising before and after, not by reading fields), and a whole encounter leaves a `CharacterSheet` byte-identical through `CharacterSheetJson`. Each carries its own control that the run did something.

### The broken twin

`PlayEngineTwinTests` runs the **byte-identical** examples against a copy of the rules carrying one documented substitution: `special_effects.interpretation.duration_rounds`, `up` to `down`. `WithDefect` reads the shipped bytes and **throws if that line does not occur exactly once** — zero means the twin has stopped reproducing anything and would pass for the wrong reason; more than one means it is not the single change it documents.

Three properties of it are load-bearing:

- **It turns two examples red, not one**, and that is a property of the page rather than of the twin: p.76 prints one exchange, and an effect lasting two pages instead of three is not the effect the escape example is about. Both are named with the message each has to produce, so a twin that broke for an unrelated reason cannot be read as a working negative control.
- **The other six stay green**, and a fourth test requires the twin's other four files to be the shipped bytes — otherwise "six stay green" could be a coincidence.
- **It also proves the engine consumes the interpretation rather than assuming a direction.** An engine that hard-coded the rounding would leave the twin green, and the twin test would fail saying so. That was watched: substituting `Half(net, entry.Interpretation!.DurationRounds!)` for `Half(net, "up")` turns the twin red for exactly that reason.

## What is real, and what says `NotYetImplemented`

**Real intents**: `Attack` (with lethal/subdual/psychic, one of p.75's five `AttackType` rows, a special effect, all-out, charge, area, team, p.75's `Cover` with the obstacle's `CoverStructure`, and p.76's `Item`), `Move`, `Hold`, `GrappleIntent` (grab, hold, escape — a grab naming the object it is aimed at), `Toss`, `BreakFree`, `Stabilise`, `EndTurn`, `EndPage`, **every Resolve purchase Chapters 4 and 5 print** — `ExtraDice`, `Reroll`, `SeizeInitiative`, `AvoidFatalDamage`, `Stabilise`, `InstantRecovery`, `KeepingHold`, `Knockback`, `Luring` and `TeamAttack` — and **every one of p.85's four Adversity purchases** — `AnythingResolveCan` naming one of the purchases on `Encounter.AdversityBuys`, and `SuppressFlaw`, `Misfortune` and `Villainy`, each of which takes the GM's own words in `SpendAdversity.Narration`. `SpendResolve` has no `default` branch any more: a member of the enum with no branch is a compile-time hole rather than a silent refusal.

### Not applied, and named in the code so the two lists cannot drift

**`Encounter.EntriesNotYetApplied` is empty**, and the field is kept rather than deleted. p.75's three situational modifiers were the last three entries on it and are applied; before them went Chapter 4's four Resolve purchases and Chapter 5's three Adversity ones — `keeping_hold`, `knockback`, `luring`, `team_attacks`, `adversity_spend_suppress_flaw`, `adversity_spend_misfortune` and `adversity_spend_villainy` — and what each of *those* cannot reach is recorded below rather than as a whole entry nothing runs.

**What the empty field is worth is the guard around it.** `PlayEngineStepTests` requires the set, this section and [`mcp-play/PLAY-POLICY.md`](../../mcp-play/PLAY-POLICY.md) to agree in all directions, empty included — so the next entry this engine declines to apply cannot be added to the code and left out of the two documents that publish it, and cannot be added to a document and quietly left unimplemented. It also drives every purchase through `Step`: none refuses, which is what makes "nothing on this list is a spend" a measurement rather than a sentence.

**The default statement is what the three modifiers cost to keep true**, and it is now a statement about defaults rather than about absences: a figure off this engine was measured **in clear air, in the open, against somebody the same size** unless the run said otherwise — `Visibility.Clear`, no `Cover` on any attack, and every `Combatant.Size` at `SameSize`. Each is the default of its field, and a `run_encounters` report echoes the light inside its `table` object so a rate carries the one of the three that is the scene's.

**`Encounter.SwitchesNotYetApplied` is empty**, and the field is kept rather than deleted, exactly as `EntriesNotYetApplied` is. **All ten gritty rules are applied**, with the initiative variant and Checking Your Swing beside them.

`RaisedGearLimit` and `GearLimitRank` were the last two on it, and what took them off was a *data* slice rather than an engine one. p.80 defines the limit as "the maximum effective Trait rank you can bring to bear **when using mundane equipment**" and points at Chapter 6 for the detail; a fight had the ceiling and neither half of what it bites on. Both halves exist now — `Attack.Item` arrived with p.76's grab, and `data/rules/play/equipment.json` carries Chapter 6's pp.87–90 — so `Encounter.GearLimited` applies them. See **p.87's Gear Limit** below.

**What that costs is the two-valued control three tests used to take from this set.** They sort ledger lines by whether they say `not yet implemented`, and a substring test whose subject can only ever answer one way is an instrument nobody has checked. The case that is left is a *clause* inside a rule that is otherwise applied — `minions_attacking`'s `the_group_bonus_does_not_apply_to`, whose own `ambiguity` says the page offers no mechanism for it — and it is a better control than the switch was, because it is written by `Step` resolving an attack rather than by `Begin` reading a flag. `PlayEngineFixture`'s `NotYetImplemented` is the one place it is built, and `TheThreeClassifierTestsRestOnAClauseThisEngineStillDeclines` is where the pair is driven.

**And the parse the two document-agreement tests rest on lost its last live table with that set.** `ListedUnder` reads the first column of the markdown table under a heading, and with both lists empty neither document carries one — so a parse that had quietly stopped finding rows would agree with two empty sets perfectly. `TheGuideTableParseCanFindRowsAndTellThemApart` drives it over a document written for it instead, in both directions: it finds the backticked rows, it skips a row that is not backticked, and a heading the document does not carry fails rather than returning nothing.

**p.80's Slow Healing is half a rule about the days after a fight, and page one says which half this scene carries.** Three clauses bite inside one and are applied for real. Nobody heals on regaining consciousness after a defeat, so p.76's instant recovery brings a character round on the Health they went down with rather than on `after_a_damaging_defeat_restores_health`. Such a character *may be conscious* at or below the figure that defeats them, which is `Combatant.ConsciousAtZeroOrLess` and is read by `Defeated` — without that the purchase would be a point spent on a sentence, since the very next line would find them defeated again. And in that condition any damage at all puts them down, which is `Combatant.Overcome`. **The question is asked wherever damage is written and not only where an attack lands one**: p.78's charge hurts the *charger*, through a path with a Health write of its own, so a character on their feet at nothing could charge a braced opponent, take the impact on the ledger and stay up — and with Fatal Damage off the clamp at the defeat figure left no trace of it in the state at all. A fourth clause is already true here and is named rather than claimed as new: stabilisation is available as often as necessary, and p.79's `Stabilise` has never counted.

**The rest is between scenes and the ledger says so** rather than leaving a reader to discover it was missing: the daily rate by Toughness band, the sentence taking away the healing after each battle — which this engine has no intent for in the first place — and the Medicine Talent's once-a-week limit and its rate. The entry's own two notes travel with them, because a reader of a run should not have to open the file: the lowest band prints no hourly figure and the `interpretation` supplies twenty-four as arithmetic rather than as a page reference, and the `ambiguity` records that the Medicine rate halves without the page saying which way.

**p.80's parenthetical is satisfied without a check, and it is the same reading `gritty_wound_penalties` already makes of the identical phrase.** "You may be conscious while at 0 or negative Health (if using the Fatal Damage rules)" hangs off the whole phrase, but exactly the defeat figure needs no optional rule — p.75 defeats a character there in any fight — and Health cannot fall below it unless Fatal Damage is on. So the condition holds structurally rather than by a branch.

**p.80's Friendly Fire needs no field at all, because the fight already knows.** "A target engaged in close combat or otherwise bunched up with other characters" is derived from p.73's range bands, which are pairwise: a target at Close Range with somebody who is not the person shooting at them is a target with somebody else close enough to catch a stray round. Defeated characters are not in the melee, for the reason they are not the actor or target of anything.

**The second attack is resolved, not announced**, which is the whole difference between this rule being applied and this rule being reported: the stray round goes through `ResolveAttack` like any other attack — it rolls, it is defended against, and it does damage or a special effect — and the one thing it may not do is trigger a third. The GM's random choice comes off `IDiceSource` so that a seeded run gives the same fight twice, and the faces are on the ledger so the choice is auditable rather than merely random. **Enough dice are thrown that every character in the melee can be the one it finds**, which one d6 cannot do: read as `(face - 1) % count` a single die reaches six candidates and no more, so a melee of nine had three characters the page calls selectable and this engine could never select. The faces are read as one number in base six and as many are thrown as span the melee — one up to six of them, two up to thirty-six. The distribution is not uniform and does not claim to be; what the fixture holds is that the reachable set is the whole melee. **What the stray shot carries is the weapon and what it drops is the first shot's declarations**: the Trait, p.75's row, the damage kind, the effect, `CloseRangeOnly` and p.76's grabbed `Item` are properties of what is being fired; cover and its Structure are a line of sight to somebody else, and all-out, charge, area, team and `VulnerablePart` are things the attacker said about the target they meant to hit. `second_attack_penalty_dice` is read and applied rather than assumed away — "this time at no penalty" is a printed number.

**p.79's Drop is pairwise in the book and exact as one global order, and that is the finding that made it applicable at all.** An order depends only on how each *pair* compares, and there are three kinds of pair: two ready characters both double, and 2a against 2b orders exactly as a against b — which is right, because neither has the drop on the other; two unready characters double neither, right for the same reason; and a ready character against an unready one doubles exactly one of them, which is the rule as printed. So doubling every holder's `EncounterState.EffectiveEdge` once produces the same order as comparing every pair under p.79's own sentence, with no case left over. **Where it meets p.73's seize, both answers are readings and both are in the table below**: a seizer still goes first, because seizing is not an Edge effect at all; and a ready character who has seized under the GM's alternative acts on four times their figure, because two printed sentences each double an effective Edge and both are triggered. `Combatant.Ready` is the caller's word and it is the sharper version of `Invisible`'s argument: carrying a gun is a capability and having it levelled is a state, nothing in Chapters 3–5 levels one, and p.79 hands the question to the GM in as many words — `final_say` is on the entry and on the ledger.

**The other half of the rule is pairwise and is named rather than applied**, beside the clauses `team_attacks` and `minions_attacking` leave to a person. `also_held_by` gives the drop to a character with a ranged weapon "against anyone moving up to them to engage them in close combat" — held against one opponent and not against the rest, which one order cannot carry, because doubled against one and not another admits a cycle: A beats B, B beats C, C beats A. A ready group of Minions is a second no-op the ledger names rather than performs: p.73 gives them no Edge, so there is nothing to double.

**p.79's Close Range rule needs three facts and each is read where it lives.** That the pair is at Close Range is `EncounterState.Ranges`, which is pairwise because p.73's bands are. That the attack is *ranged* comes off p.75's table — a row whose printed type names *Ranged* is one, and the rows whose attacking Trait is the table's bare `Power` column are the ones the table declines to classify. For those the answer is on the sheet: `Combatant.RangedPowers` is every Power id whose **own Ch.2 Range** is `ranged`, filled by `CombatantFactory` the way `Powers` is, because a Blast reaches across the street and a Growth does not and neither `Powers` nor `TraitRanks` can tell them apart. That such an attack *can* be used at Distant or Extreme is `range_classes`' own `ranged_attacks_reach`, which is exactly the question the entry's `applies_only_to_attacks_usable_at` asks; both strings are read and a pair that stops naming a band past Close is a **throw**, not a penalty applied on nothing.

**`ignored_for` is the caller's word, and the default is the page's.** Thrown weapons are printed as an *exception* to the reach rather than as the reach, so `Attack.CloseRangeOnly` is what turns the penalty off and a ranged attack reaches Distant unless somebody says otherwise. There is no equipment in a fight here — see the Gear Limit below — so nothing but the person running it could tell a pistol from a throwing knife. A declaration that turned nothing off says so on the ledger, and so does a Power the reading declined: a fist collects no penalty because p.73 never let it reach past an adjacent target, but a Power collects none because this engine read its Ch.2 Range and decided, and the two silences are not the same silence.

**p.80's Hard Targets is two rules that meet on one roll, and each half lives where its fact is.** `Combatant.HardTarget` is the caller's word — Chapter 2 has no flag that says a character is a machine, and the same battlesuit is a vehicle in one GM's game and a person in armour in another's, which is the same argument `Size` and `Invisible` are here on. `Attack.VulnerablePart` is a **declaration on one attack** and not a state of the target, because the page prices it that way: the attacker accepts `penalty_dice_to_negate_it` on *their* roll, and the next character to swing at the same machine may decline to. The doubling multiplies the rank **before** either printed halving — the page doubles a *rank*, and doubling afterwards would put an odd one through the round-up half first and hand back a die more than p.80 allows. Active defences never move, because the page says passive; a `CoverStructure` does not either, because the declaration is made on a combatant and a wall is not one. `recommended_pro_for_vehicle_scale_weapons` is named on the ledger and **not applied**: the Penetrating Pro is advice about how characters are built, and `play/` holds no opinion about Pros.

**p.85's first Adversity purchase is applied**, and it is the one that is not a rule of its own: "whatever a point of Resolve could have done, on behalf of any NPC" is the Resolve purchases with the GM's money behind them. `SpendAdversity` carries which one — a point spent on nothing in particular would be a point spent on nothing — the pool pays, and the NPC's non-existent Resolve is never touched. `Encounter.AdversityBuys` is the list of the ones it runs, kept as one list so the gate and the dispatch cannot drift, and it is **all ten** now. The four that used to refuse — `SeizeInitiative`, `InstantRecovery`, `AvoidFatalDamage` and `Stabilise` — charged the buyer's own Resolve, so an NPC could not be handed one; they go through `Charge(fromAdversity: true)` like the other six, and each keeps every limit its own page prints: a seize still lasts the rest of the fight and still doubles an Edge instead under the GM's alternative, an instant recovery is still once a scene and still refused to somebody bleeding out, and p.79's rescue still stabilises where `resolve_also_stabilises_if_necessary` asks it to. **The list survives its own emptying of the other arm**: a purchase added to `ResolveSpend` and not added here is answered `not yet implemented`, where the dispatch would throw in the middle of a fight.

**Four of the ten refuse a group of Minions, and the pages that refuse them are p.73 and p.77.** A Minion group is on `npc_kinds`, so it gets as far as the purchase, and then the purchase has nothing for it: seizing is a place at the front or a doubled Edge, and `minions_have_an_edge` is false while `minions_act` puts them after everyone else — which is the outermost key of this engine's own order, so the point would move nothing. The other three all turn on a Health total, and `attacking_minions.minions_have_health` is false: a group is defeated by bodies, so there is no defeat to come round from, no fatal threshold to be past and no clock to stop. An effect cannot leave one to shake off either, because p.77 resolves an effect against a group by taking bodies out of it. Each refusal cites the entry that decided it rather than the entry selling the purchase, so a reader lands on the page that says no. **Who it may be bought for is `npc_kinds` and is read**, the way p.85's other two eligibility lists are: a Hero is refused with nothing spent. That sentence is what makes this a purchase at all, and it was the half nothing read — every one of the six purchases was reachable for a Hero, so a point of the GM's pool bought a Hero the die their own Resolve would have bought, which is the one thing a two-pool economy exists to make impossible. The other three Adversity spends are rules of their own, and each is a scene rather than a roll — see below.

**Each of those four refusals quotes the field it was derived from, and the field is read back out
before it does.** The line says "p.77 gives them no Health at all (`minions_have_health` is False)",
which is a claim about a printed page made by interpolating a value — so an entry corrected the
other way would have gone on refusing and printed *its own contradiction*. `edge_ties`'
`minions_have_an_edge` and `minions_act` and `attacking_minions`' `minions_have_health` are
therefore throws when they stop saying it, the same shape as `gritty_the_drop`'s and
`seize_initiative_gm_alternative`'s printed words. `minions_act` is the sharper of the three,
because the order of action turns on the same phrase: a group that had stopped acting last would
have been refused a seized initiative on the grounds that the order would not move, while it would.

**A purchase priced below a whole point is refused rather than paid backwards, and the number of
points is the caller's.** Two things read it and neither could see the case. p.85's pool gate
compares the pool with what the *intent* asked for, and nine of the ten purchases charge their own
printed price and ignore that figure — so a spend of `0` points walked the gate on an empty pool and
then charged one, leaving the GM on **−1 Adversity**. p.84's dice purchase multiplies by the figure
instead, so `−5` points took a cost of −5 out of a pool: the GM's pool *grew*, and a Hero buying −5
dice minted five Resolve the same way, with `CannotAfford` unable to see it because a pool is always
at least a negative cost. Every price in Chapters 4 and 5 is a whole number of points and none is
below one, so both are ledger refusals now, with `Combatant.Spending` throwing on a negative cost
behind them.

**p.85's suppress-a-Flaw spend: what is state, and what is narration.** One point stops a Flaw "getting the better of" a Villain, a Foe or an Extra "for the rest of a scene", and no character may benefit "more than once per issue". **Nothing in `play/` makes a Flaw bite** — the page says an NPC's Flaws come into play "whenever the opportunity presents itself", which is a GM's judgement and not a roll — so *what the suppression saves the character from* never reaches the state, and the ledger line says in as many words that it is the GM's to narrate. Everything the page states in figures does reach it: `cost_adversity` leaves the pool exactly once, only the three kinds on `eligible_characters` may be bought out (a Hero or a Minion group is refused by name, off that list rather than off a list here), and `Combatant.SuppressedFlaw` carries the Flaw the GM named. **That field is read**, which is what keeps it from being a flag nothing looks at: the second purchase against the same character is refused, and it is on the public state the encounter server publishes. A purchase that names no Flaw is refused with nothing spent, the shape a lure that names nobody is refused in — this engine holds no Flaws, so an unnamed one would put "some weakness or other" on the ledger.

**p.85's misfortune: the pool is the whole of the mechanism, and the entry says so.** One point throws "a misfortune at the Heroes". The entry's own `ambiguity` records that **nothing here is mechanical** — a misfortune is three examples and two prohibitions, with no roll, no threshold, no duration and no way of resisting one printed anywhere — so a point leaving the pool is not most of this rule, it *is* this rule, and an engine that invented a mechanic for it would be inventing one the book does not have. What the ledger carries beside the point is the GM's own sentence, taken off `SpendAdversity.Narration`: **a spend that does not say what the misfortune is is refused with nothing spent**, because a pool that has moved with no words behind it is a line nobody can narrate from and nobody can audit. The line quotes what the page asks of one — a challenge rather than a punishment, never a heavy-handed plot device — and says the misfortune itself is the GM's to narrate.

It is also **the one spend aimed at a side rather than at a character**, so its `Actor` is not read and its ledger line names none: p.85 throws it at "the Heroes", and the line names the side they are on. There is deliberately **no "nobody to throw it at" refusal**: the opening pool is a point per Hero plus the Challenge Level times the same number, so a fight with no Hero in it opens on nothing at all and the spend is refused for want of a point long before it could be refused for want of a target. A guard no encounter can reach is worse than none, and the fixture drives that rather than asserting it.

**p.85's act of villainy: the limits are the engine's and the act is the GM's.** Once per story, one point has a Villain "automatically perform an act of villainy, meaning anything necessary to advance the story". Advancing a story is not something this engine has, so what the Villain does never reaches the state and the line hands it back — but every figure on the page does reach it: the pool pays once, only a `Villain` may be handed one (`excluded_characters` names Foes and Minions, and the refusal quotes it), and `EncounterState.Villainy` records that the story's one act is spent, which is what refuses the second. A purchase that does not say what the act is is refused with nothing spent, because the act is the purchase.

**What a team attack cannot coordinate**: `team_attacks`'s `participants_act_at` — "the end of the page" — and `all_participants_must_target_the_same_enemy` both describe several characters acting as one, and a `Step` is one character's action. The `attack_bonus_dice`, the per-target-per-battle limit and the exploding sixes are applied; the ledger line beside the bonus names the two clauses that are not. `the_limit_may_be_lifted_by` is "the Heroes being clever about it, or the GM ruling otherwise", which is a person's decision: the refusal quotes it, and a caller who has been told the GM ruled otherwise attacks without the flag.

**What a lure cannot hit**: `luring.redirects_to` is "whatever lies directly behind you", and Chapter 7 does not settle it. An obstacle carries a Structure now, but a Structure is a *passive defence* — what an obstacle offers a target hiding behind it — and nothing here gives an object Health or a defeat of its own, so there is still nothing for the redirected attack to land on. A lure that names nobody is **refused rather than charged for** — the attack had already missed the buyer by at least the margin p.79 asks for, so a point taken for it would buy a state change nothing could receive, which is the shape of defect this guide's ledger rules exist to prevent. Naming a person is what `SpendResolve.Target` is for.

**What a knockback hits**: `knockback`'s `damage_on_striking_a_solid_object`, `the_object_must_be_tougher_than_the_target` and `a_passive_defense_above_the_objects_structure` all need a thing with a Structure, and Chapter 7's three object tables rate fifty-eight things, forty-two of them with a Structure — see **Chapter 7's scenery** below. `SpendResolve.SolidObject` names one and the clause is applied: half the blow again, unless the target's best passive defence exceeds the Structure. A purchase that names nothing keeps the line it always had, so a reader is not left to assume the extra damage was rolled; one that names something no page rates is refused with nothing spent. `target_falls_prone` is on the line and nowhere else on purpose: **the book attaches no mechanic to being prone.** All four printings of the word — p.78's here, and Hyper Breath, Shockwave and Slick in Chapter 2 — either pair it with losing the next turn to act or leave it as description, and nothing anywhere rolls against it. A `Prone` flag would be a state nothing reads.

**One clause inside a rule that is otherwise applied**: `minions_attacking.the_group_bonus_does_not_apply_to` — the size bonus is not supposed to count towards penetrating cover or hurting somebody behind Armor or a Force Field. The entry's own `ambiguity` is why it is not applied: both of those are decided by the same attack roll the bonus is granted to, so read strictly it asks for two attack totals against one defence roll and the page offers no mechanism. The ledger line says so rather than claiming the bonus is "on the attack roll and nothing else", which is what it used to say. The per-target caps in the same entry **are** applied.

**Fatal Damage is a clock, not a floor.** With that setting on, lethal damage past `dying_begins_when_lethal_damage_reduces_you_to` starts a character bleeding at `dying_damage_per_page`, ticked at `EndPage`, until `dying_ends_at` — stabilisation or the negative of their full Health. Three things stop it: p.79's `Stabilise` roll (the Trait `stabilise_roll` names, at its own difficulty and threshold), `cost_resolve_to_stabilise_immediately`, and the Fatal Damage rescue itself, which `resolve_also_stabilises_if_necessary` makes do both. `instant_recovery_requires_being_stable` is why p.76's instant recovery is implemented here rather than listed as unimplemented: a rule *about* a purchase cannot be read while the purchase is a stub. `stabilise_also_by` — "a Power like Healing" — is prose and a GM's call, so the ledger names it rather than applying it.

**Two ways to be out of the fight, and both are on `Combatant`**: beaten down to `damage.defeated_at_health`, and p.76's `DefeatedByEffect` — an effect whose duration reached what was left of the target, which lasts the rest of the scene and is not a Health total (an Ensnare that ends a fight does it without a point of damage). `Defeated` reads both, so `Over`, `RunToEnd` and the policy all see either. **A defeated combatant is refused rather than resolved**: every intent that is a character *doing* something — `Attack`, `Move`, `Hold`, `GrappleIntent`, `BreakFree` — is refused for a defeated actor and against a defeated target, citing whichever of the two rules put them there. **Chapter 5's Resolve purchases are deliberately not guarded, and Chapter 4's four are.** The unguarded ones are exactly what a character who has just gone down does: p.76's instant recovery and p.79's Fatal Damage rescue are both bought from there, and refusing them would make the two purchases the book prints for that situation unreachable. Keeping a hold, knocking somebody across the street, luring and leading a team attack are things a character does while they are still in the fight, so `KeepingHold`, `Knockback`, `Luring` and `TeamAttack` refuse a defeated buyer, citing whichever rule put them out.

**Grappling is four states, not two.** `Grapple` records the *move* as well as the band, because p.76 gives them different consequences: a full **hold** is control over a person and leaves them only trying to escape, a full **grab** is control of an *object* and restrains nobody, and a partial grab or hold takes both characters' active defences away *against anyone else* — the character they are tangled with is the one they can still meet. A partial hold additionally leaves both of them one physical action, "an opposed Might roll". Two of those were applied to nobody and one was applied to the wrong person: every full grapple immobilised its loser, so a character who had lost their sword could not dodge.

## p.76's grab, and the object it is aimed at

**A grab is aimed at an object and a hold at a person, and that is the whole reason a grab has to name one.** p.76: a grab is "an attempt to take a weapon or other handheld item away from your opponent"; a hold is "an attempt to control or restrain your opponent". So `GrappleIntent.Item` is **required by a grab and refused when it is missing, with nothing rolled** — a grab of nothing is a hold by another name, and resolving one would put a contest over nothing in particular on the ledger and, at three net successes, hand somebody control of it. It is the shape of refusal p.79's lure that names nobody makes.

**The object is the caller's word, for the reason `Size`, `Invisible`, `HardTarget` and `Ready` are.** There is no inventory here and there cannot be one: an attack names a Trait and never an item, a `Combatant` carries no gear, `play/` may not read `data/rules/`, and there is no Weapon Bonus anywhere in this repository's rules data — the same four absences that make p.80's Gear Limit inapplicable, recorded above. What this engine claims about the word is only what p.76 states.

**But whether the opponent *has* one is a fact, and taking that off the grabber's say-so too was a line that lied.** p.76 aims a grab at "a weapon or other handheld item away from your opponent", so a grab presupposes an opponent holding something — and nothing could say that anybody was. A full grab against a target holding nothing announced that the winner had the sword, that the loser was "not restrained by it", and that what losing it meant for the loser's own attacks was the GM's, about a character who had never had it; on the wire, where no combatant could open a fight holding anything, **every** grab was of exactly that kind. So the opening hand is one more caller's-word field — `Combatant.Carrying`, the wire's `holding` on a combatant at `start_encounter` — and **a grab for an item its target is not recorded as holding is refused with nothing rolled**, the same shape as a grab that names none. The refusal names what the target *is* holding, because "they have not got that" sends a caller guessing.

**The one exception is the page's own, and without it the deadlock would have no printed way out.** A partial grab leaves the object where it was and has the pair "make opposed Might rolls on your turn to act to try gaining control" — so the character who walked in with it rolls against a grabber who is not holding it either, which the guard above would refuse. `Contested` widens the guard by exactly that: a grab is allowed for the object a standing partial grab between these two is over. A partial grab takes both characters' active defences away against everybody else, so a contest nothing could end would take them away for the rest of the fight — which is the defect this slice already fixed once, reached by another route.

**An item carried in is stamped `HeldItem.BeforeTheFight`, and that is not page zero.** p.76's one page is a limit on what a *grab* wins; nothing in Chapters 3–5 takes a weapon off somebody who simply brought one. The page a fight opens on is 1, so a carried item is never the item a page turn drops, and the wire reports `won_on_page: null` beside `carried_in: true` rather than publishing the engine's 0 as though somebody had won it on a page no fight has.

| Clause | Where it lives |
|---|---|
| "you and your opponent are fighting over an item" | `Grapple.Item`, on the **one** record that names both characters — the deadlock is a fact about the pair, so a copy on each would be two places for one fact to rot in |
| "they can't use it, but neither can you" | `Attack.Item` naming the contested object is refused for **either** party while the partial grab stands. It bites on an attack alone: the same paragraph makes letting go the way out |
| "you gain control of the object" | `Combatant.Holding`, a `HeldItem` carrying the name, the page it was won on and whether it has been swung. The loser stops holding it where a previous grab had put it there |
| "use it … on that same page" | `Attack.Item`, refused by name unless the actor holds exactly it |
| "or toss it aside" | the `Toss` intent, refused the same way |
| "you can exit grappling combat at any time by letting go of the object" | the same `Toss` intent, by **either** party of a partial grab and over the contested object — it ends that grab and both of them have their active defences back. Nobody gains control: only a full grab is that |
| "on that same page" | `EndPage`: an item won on the page that is ending and neither used nor tossed is tossed aside, and nobody holds it |
| *(unwritten)* what becomes of it when its holder is defeated | `EndPage` again, after the dying clock: a character who is out of the fight lets go of whatever they hold, whoever won it and whenever |
| "without suffering a multiple action penalty … in effect a free action" | nothing, and the ledger says so — this engine does not count actions per page at all, so what the clause buys here is that the use or the toss does not spend the turn. A fixture drives exactly that: the holder tosses and still attacks |

**What the item does *not* do is the half most worth stating**, because an engine that quietly did it would be inventing a figure. Naming an item on an attack moves neither the row of p.75's table nor the damage, and until Chapter 6 was extracted it moved nothing at all. **It moves the pool now**, and only through p.87's Gear Limit — see below — which is a figure read out of `equipment.json` rather than one this engine has an opinion about. And **what losing a weapon means for the loser's own attacks is the GM's**, said on the ledger rather than silently not done: no sheet says which Trait a weapon backs, so there is no figure of theirs to dock.

**An item that was used survives the page turn, and that is why `HeldItem.Used` exists.** The page gives the winner one page to use or discard the object; an item they actually swung is one the page has stopped talking about, so the drop no longer applies and what becomes of it is the GM's. Without that field the two branches would be one, and either a used weapon would vanish at the page turn or an unused one would be carried silently into page four — a state the book does not describe.

**A partial grab had no way out, and p.76 prints one in the same paragraph as the deadlock.** "You can exit grappling combat at any time by letting go of the object." The half-measure takes both characters' active defences away against everybody else and is otherwise settled only by three net successes — so a fight in which neither ever rolled one was a fight in which two characters could not dodge anybody for the rest of it. Neither could quit: the character who walked in with the object could toss it and stay tangled, because a toss dropped an item and touched no grapple, and the one grabbing at it could not toss it at all, because a toss was refused unless the actor held what they named. `Toss` is now both — the same intent, because it is the same act — and the ledger line says which. **Nobody gains control of the object by a concession**, because only a full grab is "control of the object" and treating a concession as one would be a fourth outcome for a table that prints three.

**A grab between the pair is replaced whichever way round it was recorded.** The filter used to match the actor as `Grapple.Holder` only, so a character who won a partial grab and then lost the item outright left their own partial standing beside the winner's full one — and a partial grab takes *both* characters' active defences away against everyone else, so a contest nothing could end took them away for the rest of the fight. One contest between two characters is one record; the same now holds for a hold.

**Mechanics with no intent yet**: multiple actions and their −2d, combat stunts, ambushes, clobbering attacks, defending others, healing between fights, **the rest of Chapter 7** — falling, energy and its nine types, hostile environments, suffocation, swimming, leaping, lifting, scorching, smashing something on purpose, disasters and the toxin tables, none of which has an intent to call (p.108's `damaging_cover` is the one entry of the chapter that is neither applied off this file nor on this list: it is p.75's cover rule printed again, and it is applied through Chapter 4's copy — see [`play-rules.md`](play-rules.md) for the check that holds the two to one reading) — and `gritty_fatal_damage`'s `resolve_may_be_spent_on_damage_you_inflict_on_someone_else` (`SpendResolve.Target` exists for p.79's luring, and the Fatal Damage rescue does not read it — buying back somebody else's blow is a rescue this engine still only performs on its buyer). None of them is stubbed; there is simply nothing to call. **The item a full grab wins was the last named row of this list and is off it** — see below.

## p.75's three modifiers, and where each fact had to live

The MODIFIERS block prints three rules and **each one is a fact about a different thing**, which is the whole of why they were the last three entries left unapplied: none of them is a property of an intent, and putting all three on one would have been three wrong answers.

| Modifier | Where the fact lives | Why there |
|---|---|---|
| **Cover** | `Attack.Cover`, `Attack.CoverStructure` | Cover is a fact about a **line of sight**. The same wall hides a character from the shooter in front of it and from nobody behind it, so a field on the fight would be a claim about everybody at once. |
| **Size** | `Combatant.Size`, a `double` the caller sets | Size is a property of a **character**, and it is the caller's because Ch.2 has no size stat — see below. |
| **Visibility** | `EncounterState.Visibility`, set by `Begin`; plus `Combatant.Invisible` | The light is a fact about the **scene** — the smoke is the same smoke for everybody in it. An opponent nobody can see is a fact about a **pair**, which p.75 states separately and which is a state rather than a capability. |

**The compensating Powers are the one half read off a sheet**, because they are the one half that is a capability. `CombatantFactory` fills `Combatant.Powers` with every Power id on the sheet **whatever its rank**, and the visibility modifier looks `powers_that_compensate_given` up in it. It cannot use `TraitRanks`: Blind Fighting and Radar are default-rank Powers, so `DerivedStatsCalculator.GetEffectiveRank` answers **0** for both by design, and a rank of 0 cannot tell "has Blind Fighting" from "has never heard of it". The ledger line names the Power that compensated.

**Every modifier that applies writes a line** naming the entry, its `source_ref`, the band's printed word and the dice it moved — and the dice are always the file's. What is *not* the file's is what four English phrases mean as a comparison, which is a reading and is in the table below.

**The pool after modifiers goes through the sub-1d floor like any other**, because it goes through the same `SuccessCounter.Roll`: a −3d on a 2d pool asks for −1 dice, one die is thrown, and it scores only on a six and only one success even then. A fixture drives exactly that and counts the faces consumed, because "the floor applied" and "the roll was skipped" look identical from the successes alone.

## The readings this engine makes, and why each is here rather than in the data

`play-rules.md` states the discipline: **a fact field is a claim that the page states the thing**, and a reading is labelled, kept out of the transcription, and derived from something printed. These are the engine's, and they exist because a simulator cannot decline to pick.

| Reading | Why the data cannot answer it |
|---|---|
| **Only a Power whose own Ch.2 Range is `ranged` reaches past Close Range**, for p.79's Close Range rule. | p.75's table declines to classify its two Power rows — their attacking Trait is the bare `Power` column — and Chapter 4 has no per-Power reach. `self` and `touch` plainly cannot be used at a distance; `zone` and `special` are neither said to nor said not to, and the rule is a *penalty*, so the narrow reading never costs a dodger dice the page may not have meant them to lose. **The data says the switch still carries**: of the 141 Powers, 21 print `ranged` and Blast is one of them, so the archetypal ranged attack pays the penalty and a measurement under this setting is a measurement of it. What it leaves out is the nine `zone` Powers and the four `special` ones — Dazzle, Shockwave, Slick and Hyper Breath among them — and **a Power the reading declines now says so on the ledger**, because a switch that is on and did not reach an attack is the case this engine's ledger exists to make visible. |
| **p.79's Drop is applied as one global doubling of every ready combatant's Edge.** | The page's doubling is pairwise and an order is not — but an order depends only on how each pair compares, and doubling both, neither, or exactly the ready one of a pair is the printed rule in all three cases. So the global form is exact rather than approximate. The half that is *not* expressible — a shooter's drop on whoever closes with them — is named on the ledger instead, because doubled against one opponent and not another admits a cycle. |
| **p.79's Drop does not overtake p.73's seized initiative**, and a ready character who *has* seized acts on **four times** their Edge under the GM's alternative. | Neither page mentions the other. Seizing puts a character "first on every page of the action" rather than moving a figure, so composing the two the way this engine composes everything leaves a seizer in front of any doubled Edge — and where the GM has taken the alternative, two printed sentences each double an *effective Edge* and both are triggered, so they multiply. Nothing settles the second against capping it at twice; it arrives out of two unrelated branches, which is why it is written down here rather than left to be discovered in an order. Both are driven, and the fourfold one with figures only the fourfold answer wins. |
| **A hard target's passive rank doubles before either printed halving, not after.** | p.80 doubles a *rank*, which is the figure on the sheet; p.75's table and `lethal_and_subdual` then halve what answers this attack. The page never has to say which comes first because it prints no odd case, and the two differ there: a Toughness of 7 is 14 then 7 one way round and 4 then 8 the other, which is a die more than p.80 allows. |
| **A cover's Structure is never a hard target.** | A wall is plainly one of the "thick, inanimate objects" p.80 names, but the declaration this engine takes is made on a **combatant** and a wall is not one — the Structure is a figure supplied for one attack — the caller's, or a row of Chapter 7's — so a caller who wants a doubled wall states the doubled figure. Same shape as the knockback's solid object. |
| **Slow Healing's "(if using the Fatal Damage rules)" is satisfied structurally rather than by a check.** | Exactly the defeat figure needs no optional rule — p.75 defeats a character there in any fight — and Health cannot fall below it unless Fatal Damage is on. It is the same reading `gritty_wound_penalties`' own `interpretation` makes of the identical parenthetical. |
| **An odd pool banks the even half.** 11d taking automatic successes banks 5. | `automatic_successes`'s own `ambiguity`: the rule is priced in pairs and the printed example is 12d, which settles nothing. Integer division is the reading that never gives a character more than the page promises. |
| **A Toughness is halved once, however many printed rules say to halve it.** The table's `1/2 Toughness` rows (p.75) and `lethal_and_subdual`'s lethal clause (p.75) can both fire on one figure. | The two agree wherever the book's own defaults hold — the unarmed row is one of `lethal_and_subdual`'s two named subdual sources, and everything else physical defaults to lethal — so the page never has to say. Where a caller puts them at odds, halving twice would take a Toughness of 12 to 3, which no row prints. p.81's Example of Combat is what settles the shape: the mecha's Might attack is answered by 12d Armor at its full rank, the table's "Power" column doing the work with no halving in sight. |
| **"Power", in the defence column, is any defence Trait the table never names by name.** | p.75's table prints a bare `Power` beside Agility, Toughness and Willpower and says no more. Deriving the set from the table's own other columns is the reading that cannot drift from it. |
| **A charge's impact is the charger's own net against their own attack roll, at the damage rate, less what the target took.** | p.78 says the charger "makes their own passive defense roll against the attack" and that the self-damage is "reduced by the damage inflicted on the target", and prints no arithmetic. The attack roll's successes are the only threshold on the table; `damage.damage_per_net_success` is the only rate the book has; and the subtraction floors at nothing, because a charge that hurt the target more cannot heal the charger. |
| **A charge may be rolled with Might, Density, Growth or a Travel Power.** | `charge_attacks.attack_traits` lists three ids and one piece of prose — "any Trait usable for a close combat attack" — and Chapter 2 has no close-combat flag. The narrowest reading that keeps every charge the book describes legal is the attack Trait of p.75's two close-combat rows, which is Might. |
| **An `Encounter` is one scene, so "the rest of the scene" is the rest of the fight.** p.85's suppressed Flaw is carried to the end and never expires inside one. | The page measures the suppression in scenes and this engine's largest unit is the encounter: `Step` turns pages, and nothing in it ends a scene. A duration that expired on some page number would be a clock the book does not print. |
| **A story is this encounter, so "once per story" is enforced across one fight and no further.** | p.85's villainy is the only rule in Chapters 3–5 measured in stories, and the entry's own `ambiguity` says a story is a unit the chapter defines nowhere — the pools it governs are counted per issue, and the two coincide only in a one-session game. A scene is the largest thing this engine can see. Enforcing the limit over a unit it cannot see would be a limit it could not honestly claim, and enforcing none would drop a printed one; the ledger line says which unit it counted in, so a GM opening the next scene knows the count did not travel with them. |
| **The suppress-a-Flaw limit is refused per character, not per Flaw.** | The printed sentence names a character — "no character can benefit from this more than once per issue" — and the entry's own `ambiguity` says the two readings differ for anybody carrying two Flaws. The refusal quotes the ambiguity rather than settling it, and per character is the half that never allows more than the page does. |
| **That limit is counted over this encounter, so "once per issue" is once per fight.** | Same shape as the story above, and the *permissive* direction: an issue is several scenes, an `Encounter` is one, and a GM running four scenes gets four suppressions per character where the page allows one. Nothing here can see an issue, so both lines that mention the limit say which unit they counted in and hand the count across scenes back to the GM. They used to say "this issue", which is a claim about a unit this engine has not got. |
| **A held character's Powers are refused rather than adjudicated.** | `hold` says a held character may use "any Power they could reasonably use while physically restrained", `adjudicated_case_by_case_by: gm`. That is a judgement and this engine has nobody to ask, so it applies the clause it can — "only trying to escape" — and the refusal names the clause it could not. |
| **A grab is refused unless its target is recorded as holding the object, and what they are holding is the caller's word.** | p.76 aims a grab at an item "away from your opponent", which is a claim about the opponent's hands, and there is nothing here to look a hand up in. The alternative to a declared opening hand is taking the object's *existence* off the grabber as well as its name — which handed a winner control of a thing nobody had ever carried and printed a line about what its loss meant for a loser who had never had it. It is the same shape as `Size` and `Invisible`: a fact Chapters 1–5 give this engine no way to derive, defaulted to the arrangement every figure here is measured under (empty hands), and refused rather than invented when a caller has not supplied it. The cost is that a fight opened without the field has no grab in it at all, which the refusal says in as many words. |
| **The object a grab is aimed at is the caller's word, and a grab that names none is refused rather than resolved.** | p.76 tells a grab from a hold by what it is aimed at, and there is nothing here to look an object up in: an attack names a Trait, a `Combatant` carries no gear, `play/` never reads `data/rules/`, and the rulebook's own gear catalogue is not extracted. The alternative to the refusal is resolving a contest over nothing in particular and, on three net successes, handing somebody control of it — which is the shape of line this engine's ledger rules exist to prevent. |
| **What losing an item means for the loser's own attacks is the GM's, and no figure of theirs moves.** | p.76 says the winner gains control of the object and says nothing at all about the loser's rolls. Nothing in this repository's rules data says which Trait a weapon backs, so docking a Might for a lost sword would be inventing a figure no sheet supports. Chapter 6 prices the weapon and not the wielder: a Weapon Bonus is added to whoever is holding it, and its absence from somebody's hands is exactly the state this engine already records. The ledger line names the question rather than leaving a reader to assume it was handled. |
| **p.87's Gear Limit reaches an attack made on one of p.75's two weapon rows, and no other.** | p.87 caps what a Trait can apply "when using mundane equipment", and the Attack and Defense table's type column is the one classification this engine has for what an attack is made with. The two weapon rows are equipment being used. The two Power rows roll a Power's own rank, which is not equipment and which p.88 never adds a Weapon Bonus to — it adds one to Might, Martial Arts or Agility and to nothing else. `Unarmed` is a fist by the table's own word. Each of the three writes a line saying which silence it is, because a rule that is on and did not reach an attack is what this ledger exists to make visible. |
| **p.87's close-combat exception is the caller's to take, and is not applied on top of the cap.** | "If your unarmed attack or defense rank exceeds your effective rank while armed with a melee weapon, you can use your unarmed attack or defense rank instead" is printed as a permission, and the entry's own `ambiguity` records that the page never says who takes it or when it is declared. A caller who has been told the wielder takes it declares p.75's `Unarmed` row with the item still in hand — full Trait, no cap — and the damage kind the weapon still buys is the `Attack.Damage` they already declare. Substituting the higher figure silently would be this engine deciding a choice the page hands to a person, and would make the cap unreachable in close combat. |
| **The Weapon Bonus is part of the *attack rank*, not a modifier on the roll.** | p.90's feature glossary calls "your Trait plus the item's Weapon Bonus" the attack rank three times over and p.87 calls the sum the maximum effective rank — so it is what answers a cover's Structure, what p.78's guard on going all-out compares, and what p.78's knockback throws a target by. `AttackModifiers` is where cover, size, the light and going all-out lend or take dice, and none of those is anybody's rank. |
| **An item is matched to a printed weapon by the longest printed spelling in the caller's phrase, and an item nothing matches — or one two rows match equally — gets no bonus.** | There is no inventory here: the object a fight opens with is a phrase somebody typed, for the reason `Size` and `Invisible` are. So "a basic sword" is p.89's `Sword` and "a battle axe" is `Battle Axe` rather than `Axe`, because the longer name wins. **The printed order is a sort key and not a name**: the tables are alphabetical, so eight rows are filed inverted — `Rifle, Sniper`, `Pistol, Snub`, `Shield, Spiked`, `Shotgun, Automatic`, `Blast Rifle, Military` and the three grenades — and matching the printed string alone reached none of them while silently pricing five as *another row*: a sniper rifle as the Rifle at +3d for the page's +4d, a snub pistol as the Pistol at +2d for +1d, a spiked shield as the subdual Shield. Each row is matched by its printed name and by that name uninverted, longest matched spelling wins, and a hyphen reads as the space it stands in for. A rolled-up newspaper is priced by nothing Chapter 6 prints, and "his shield and dagger" is priced by two rows at once — **a wrong match is worse than no match**, so both say the figure is the GM's rather than supplying a plausible one. |
| **A defeated character lets go of what they were holding, at the page turn.** | p.76 says nothing about it, and the two silences are not equally honest. The clause that puts an object in anybody's hands is "a full grab means you gain control of the object", and a defeated character controls nothing — every intent that is a character *doing* something is refused for them, and a grapple *against* them is refused before it is rolled. So an item left on a body is an item out of the fight for good with nothing on the ledger to say it had gone, which is worse than a state the book stops describing. It is applied at the page turn rather than at the moment of defeat because there is no such moment here: damage, a special effect and p.79's clock all put a character out through paths of their own, and `Defeated` is computed rather than recorded. The page turn asks the question once, after the clock. Where the object landed is the GM's. |
| **An item a full grab won and its winner actually used stays with them past the page turn.** | p.76 gives the winner one page: "use it or toss it aside on that same page". What it does not say is what becomes of an object that *was* used, because the clause it was under has been discharged — so the page turn drops an item that was neither used nor tossed and leaves alone one that was. Dropping both would take away a weapon the page plainly allowed somebody to swing; dropping neither would keep a state the book stops describing. |
| **"Neither of you can use it" is enforced against an attack naming the contested object, and against nothing else.** | p.76's partial grab says the two of them cannot use the item. This was recorded as unenforceable — an attack named a Trait and no weapon — and an attack now names an item, so the sentence is enforceable in exactly the case the page wrote it for: the character who walked in with the sword is still recorded as holding it, and would otherwise have swung the thing they are wrestling over. Both parties are refused, and the grabber for the page's reason rather than for their empty hands, so the refusal is asked before the hand is. It refuses an *attack* and not a toss, because the same paragraph prints the exit — "you can exit grappling combat at any time by letting go of the object". What is still not enforced is any wider notion of use: this engine has no other roll an object could appear in. |
| **A combatant's size is the caller's word.** | Ch.2 has no size stat. The one place the book turns a rank into a size is Growth's and Shrinking's rank-to-*height* tables (pp.30, 39) — printed in the rulebook, and in **no file this project may read**: `powers.json` carries the prose and no table, `play/` does not read `data/rulebook/`, and typing the table in here would be a transcription in code. So a GM with a giant in the scene says so, and the engine derives the factor from the two sizes rather than accepting a band. |
| **What p.75's four size phrases mean as a comparison is supplied here.** "twice", "5 times", "half", "one-fifth". | They are English printed inside a band's own label and no modelling extracts a number from them. Same shape as `seize_initiative_gm_alternative`'s "doubles": the phrase is required to still be there and a band whose phrase this engine does not know is a **throw**, not a band quietly skipped. The `dice` are always the file's. |
| **Where two size bands both apply, the one with the greater magnitude wins.** | An attacker five times your size is also twice your size, and the page plainly means the larger bonus. Taking the narrower band is the only reading that does not make "at least 5 times" unreachable. |
| **Declaring `Attack.CoverStructure` is what says the shot goes *through* the obstacle**, and the rank test is applied at every band rather than only at complete cover. | p.75 prints the test once — "if your attack rank exceeds the cover's Structure, you can attack through it" — and what it gates is a shot passing through a solid thing; a wall does not become permeable because some of the target is sticking out from behind it. A caller who means to shoot at the exposed part leaves the Structure out and pays the band alone. The number is the caller's or `Attack.CoverScenery`'s, and the two are refused together — see **Chapter 7's scenery** below. |
| **The cover's Structure is offered after every halving and touched by none of them.** | Going all-out, charging and dodging a blast all halve *your own* defences (pp.75, 78), and a wall is not one of yours. It answers when it is the greater, which is `defense_chosen`'s own rule applied to one more candidate, and it is **passive** because the page says "as a passive defense" — so no size band moves it and p.79's luring cannot be bought off it. |
| **Which defence answers is settled before p.75's size band, and a tie goes to the target's own.** | p.75 says a defender "always use[s] the best defense available", and never has to say whether "best" is the greater rank or the greater roll, because none of its own modifiers touch a wall. Comparing the two as they stand keeps the choice a fact about the two figures rather than about how big the attacker is; it can leave a dodger rolling one die fewer than their size band would have given them, so the ledger line says which of the three comparisons held. A tie goes to the target's own because the one they keep may be active, and the Structure never is. |
| **Complete cover contributes no dice.** | The printed table stops at "almost full". What the page says about a target hidden altogether is that you cannot hit one, which is a refusal before anything is rolled; an attack that got past that refusal is one going through the obstacle rather than one shooting at a fraction of a target. |
| **Carrying Invisibility is not being invisible.** `Combatant.Invisible` is the caller's word. | Ch.2 p.32 prints "You *can* turn invisible" — the Power is a capability, being invisible is a state, and nothing in Chapters 3–5 turns one on. An engine that read the Power would have every character who owns it invisible for every page of every fight, including the ones they spent shouting at somebody. |
| **`powers_that_compensate_given` is a list of examples and the ledger says so.** | p.75 reads "unless you have a Power that compensates for this, like Blind Fighting or Radar" — the field is named *given* for that reason. The engine applies the two the page gives; a GM who rules that some other Power compensates says so by not putting that character in the dark, and the line never reads as though this engine adjudicated the question. |
| **A compensating Power answers the scene's light as well as an invisible opponent, and it cancels the band rather than reducing it.** | p.75 hangs the "unless" off one sentence — "You effectively have no visibility against an invisible opponent unless you have a Power that compensates for this" — so read alone, the printed clause covers an invisible opponent and not the dark. **The book settles it on the Power's own page and this engine may not read that page**: Blind Fighting (Ch.2, p.24) is "no penalties or adverse effects when fighting in the dark or against opponents you can't see, whatever the reason". That is a Chapter 2 entry, `play/` reads `data/rules/play/` and never `data/rules/*.json`, and the entry here files `powers_that_compensate_given` under `visibility` as a whole rather than under the invisible clause — so the engine reads the scope off the field's placement, and the reading is recorded here because the sentence that proves it is on the other side of an arrow. The ledger line names which of the two causes it answered. |
| **An attack penetrates a passive defence when the attacking Trait's rank is greater than the defence's.** p.78's guard on going all-out turns on it. | The page says "opponents who could not penetrate your passive defense still cannot" and never defines penetrating. Chapter 4 states the test once, under Cover: `modifier_cover.attacking_through_cover_requires` is "an attack rank greater than the cover's Structure". The engine reads that phrase and throws if it goes away. |
| **Dodging an area attack halves the defence rather than forfeiting a turn.** `area_attacks` (p.78) prints the two as a choice and the engine has to make one. | The page gives the choice to the defender and there is nobody to ask; halving is what keeps a fight comparable across runs, since forfeiting a turn moves a character's whole page and would make an area attack's cost depend on where in the order the dodger happened to be. The ledger names the option not taken, and a policy that could choose is what would settle it properly. |
| **The Minion cap applies to both rates.** An attack cannot defeat more Minions than are present. | `attacking_minions`'s `ambiguity`: the parenthesis is printed on the area-attack clause alone, but its second half — "or within reach" — is the phrase for an ordinary attack. |
| **Wound Penalties' deeper band replaces the shallower one.** | The entry's own `ambiguity`: the two are printed as thresholds rather than steps, and at zero Health a character is already below half of any positive Health. |
| **All-out and charge penalties expire at the end of the following page.** | The page says "until after your next turn to act", which is a turn rather than a page. This is that sentence to within a turn. |
| **The GM's alternative to seizing the initiative is a table setting.** | `seize_initiative_gm_alternative`'s `ambiguity`: no page says whether the GM's preference is fixed for a table, a campaign, or taken per purchase. A setting is the reading that makes a measurement reproducible. |
| **The GM's alternative multiplies an Edge by two.** The factor is supplied here, not read. | `seize_initiative_gm_alternative`'s effect is a sentence — "doubles the buyer's effective Edge" — and the entry carries no multiplier. The engine requires the word *doubles* to still be there and throws if it is not, rather than defaulting to 2 against a rule that has changed. |
| **A policy's attack forms are the Abilities p.75's table names plus the Powers whose own Ch.2 `category` is `Attack`** — and, for a group of Minions, p.77's one characteristic. | Nothing says which Traits a character would attack with; p.75's table is the only printed list, and its bare "Power" column is the combatant's — so *which* of theirs is a question about a Chapter 2 entry, asked in `CombatantFactory` where a sheet is read and carried on `Combatant.AttackPowers`. **The reading this replaces was "every Trait the table does not name", and it was a defect that reached a published measurement**: `TraitRanks` holds the six Abilities, the twelve Talents and every Power on one dictionary, so the complement of a five-row table is most of a character sheet — the four Low Level Pinnacle City Heroes were measured attacking Schism with `academics` and `covert`, and Schism answering with `armor`. **`category` and not `tags`**: the category is a field the character engine already reads mechanically (it decides a Power's default `AffectsResolve`), while `PowerModel.Tags`'s own doc comment says no mechanic reads it and that it is not verified against a page. The cost is stated rather than hidden — three Powers carry a descriptive `attack` tag without the category, Spinning among them, and a character built out of one attacks with the Ability the table gives everybody instead. |
| **"The opponents seem faster or stronger" is read as the Edge, and "stronger" is not read at all.** `standard` seizes where the greatest `EffectiveEdge` on the other side is greater than its own. | The owner's sentence is about an impression at a table. The only figure in Chapters 3–5 about being *faster* is p.73's Edge, and the comparison is against `EncounterState.EffectiveEdge` rather than the sheets because that is the figure the order is actually built on — p.73's optional random initiative replaces it for the battle and p.79's Drop doubles it. "Stronger" has no single figure at all, since a rank is per Trait, so it is left unread rather than read badly. |
| **"In response to the other side spending" is the previous page's purchase lines, not a count of this policy's own.** | The state carries the pools and no history of them, and the ledger already records every purchase — a policy keeping its own tally would be a second record of something the engine writes down, and the two would agree until one of them was wrong. |
| **The Trait that answered an attack, and how much damage an attacker has done so far, are read back out of ledger prose.** | Neither is on `EncounterState`: the defending Trait is chosen inside `Step` and never recorded, and Health says what a character has *taken* and never who took it. Both are written by exactly one statement each, so each reading is anchored on that sentence and **throws when it moves** — the same discipline `seize_initiative_gm_alternative`'s printed "doubles" is held to. The alternative, putting the two figures on the state, would be a change to the attack resolution for a reporting convenience. The count of exchanges the first reading fails on is published rather than hidden. |
| **A group of Minions' bodies and a character's Health are ranked against each other unconverted**, so a group of three is "stronger" than a Villain on 2 Health. | p.77 gives a group no Health at all — which is why there is nothing to convert — and a target selector still has to answer. Every reading here is arbitrary in the same way; what this one buys is that it is stated, so a party that focuses fire finishes the character before it thins the mob and a reader of a rate can see that is what was measured. `StylePolicy.Standing` carries it and a fixture puts the two in one fight. |
| **`highest_threat` is damage already done, and the attack rank only until somebody has done some.** | The book has no threat figure a policy could read — Ch.4's Threat rank is a Minion group's one characteristic, not a measure of a character — and the two halves answer the same question at different points in a fight: before anybody has landed anything the only evidence is what the sheets could do. |
| **`min_max`'s all-out guard is a worst case on one opponent's *damage*, and not a distribution and not a page.** It goes all-out where the greatest attack rank on the other side, at `damage.damage_per_net_success`, still leaves it above the defeat figure. | "The counterattack cannot defeat them this page" needs the most an attack could possibly do, and the most is every die coming up a success — which is the attacking rank. A policy that modelled the distribution would be a policy nobody could argue with by reading it, and a policy is a guess that has to be arguable. **What the arithmetic does not cover is written on the method rather than left to be discovered**: everybody on the other side acts, so two opponents who could each take half of somebody's Health both pass the ceiling; p.76's special effect ends a fight without a point of damage; and with Fatal Damage on the comparison against `defeated_at_health` leaves somebody above the defeat figure and bleeding, for p.79's clock to finish at the page turn. Wound Penalties are the one omission that cannot bite — they cost a hurt attacker dice, so the real figure is under the ceiling rather than over it. |
| **`unfair` is the owner's threshold and the report says so wherever it appears.** A side at or below half over at least a hundred runs. | Nothing in the book says when a fight is too unfair; the owner does — "half or less chance of victory over a hundred or more sims". Below the floor the flag is `null` rather than `false`, because "not unfair" and "not enough fights to say" are different answers and only one of them is reassuring. |
| **Luring is decided on the roll that has just happened.** `declared_before` is "the attacker makes their attack roll". | A `Step` is the whole exchange — the attack is declared, rolled and applied in one — so there is no point between the declaration and the roll for a declaration to sit in. p.79 puts the *payment* after the roll anyway ("if your defense roll exceeds their attack roll by 3 or more, you can spend 1 Resolve"), and every condition the declaration gates is checked against the roll itself. |
| **"A physical or energy attack" is every row of p.75's table but the mental one.** | `luring.applies_to_attack_types` prints two words the Attack and Defense table does not use, and Chapter 2 has no physical/energy flag. The mental row is the one the table names, so the set is derived by excluding it rather than by listing the other four here. |
| **A knocked-back target has no weight rank, so the throwing rank is the attack rank itself.** p.78 throws them "as if by someone with a Might rank equal to your attack rank", and p.74 turns a Might into a distance. | `throwing_range.rank_formula` subtracts the object's weight rank from the thrower's Might, and nothing in Chapters 3–5 gives a character a weight rank — Chapter 6 prices gear, not people. Reading the throwing rank as the attack rank is the longest throw the sentence can mean, and the ledger line says which figure it used. The table's own `ambiguity` about ranks below 3d never arises: `throwing_range.ordinary_people_reach` covers every rank up to `table_used_when_might_exceeds`. |
| **A knockback moves the pair and no other pair.** | `EncounterState.Ranges` is pairwise because p.73's ranges are: there is no board and no distance from a fixed point, so "flies backwards" can only be expressed as the distance between the two characters involved. Where it lands is the class the throw reaches, and never nearer than they already were. |
| **A "Travel Power" is one of eight named ids.** | The entry says "a Travel Power" and Ch.2 has no such category flag; the Movement category is the closest thing and holds Powers nobody would call travel. |
| **The id breaks a tie the ladder cannot.** | p.73 says characters on the same figure and the same rung act *simultaneously*; a stepped engine has to pick an order to step in. |
| **A group of Minions cannot buy p.73's seized initiative, and the refusal settles two printed sentences against each other.** | The purchase's default effect is "you act ahead of everyone else" and the same page has a Minion group act "after everyone else" — both p.73, and they cannot both hold for one buyer. This engine's order already answers it: `minions_act` is the outermost sort key, ahead of the seize. So the point would leave the pool and the order would not move, and under the GM's alternative there is no Edge to double at all. Refusing is the reading that never charges for a state change nothing could receive; taking the other one means moving a Minion group up the order, which is a change to p.73's own placement of them and not to this purchase. |
| **A Resolve purchase is not turn-gated.** `instant_recovery.taken_on` is "your next turn to act" and this engine does not enforce it. | A defeated character has no turn to be theirs, and p.79's Fatal Damage rescue is bought in the middle of somebody else's. Enforcing the phrase would make the two purchases the book prints for a character who has just gone down unreachable. |

| **An object is matched to a printed row the way an item is matched to a printed weapon, and Chapter 6 is asked first.** | There is no scenery here either: the wall a caller names is a phrase somebody typed, so the longest printed spelling inside it wins — "a bulletproof glass window" is p.107's `Bulletproof Glass` at 6 and not `Glass` at 2, a difference of four dice. Two rows tied at the longest spelling refuse rather than pick one, because a wrong match is worse than none: the ledger would then cite a printed page for a figure that is not the one in play. **Chapter 6 before Chapter 7** is the other half: a wooden club is p.89's `Club` and p.107 rates `Wood`, and the manufactured weapon is what is in somebody's hands while the material is what it happens to be made of. |
| **A named row and a bare Structure are two answers to one question, so an attack carrying both is refused.** | Either precedence rule would put a number on the ledger the caller did not ask for. And the bare figure is not redundant: p.107 lets the GM move a Structure by as much as `gm_may_adjust_structure_by_max` for thickness or condition — the chapter's own second worked example adds one to a telephone pole — so a stated figure is how a thickened wall is said and a named row is how a printed one is. |
| **A Massive Objects row is neither cover nor the thing a knockback strikes.** | p.108's `massive_objects` prints `uses_instead_of_body_or_structure` — "the object's weight rank" — so those twelve rows carry no Structure at all, and both rules turn on one. Reading a weight as a Structure would hand p.75 a figure the page does not print for that purpose and be wrong by fifteen dice at the Empire State Building. Both are refused by name. |
| **"The target's passive defense", in p.78's knockback, is the greatest defence of theirs that `active_and_passive_defenses` does not call active — and it is not halved.** | The impact is not an attack on a row of p.75's table, so neither the row's `1/2 Toughness` nor `lethal_and_subdual`'s lethal clause has anything to bite on; it is a rank compared with a Structure. A knockback is bought off subdual damage in any case, which p.75 answers with the whole of a Toughness. The set is derived from the entry's own `common_active_traits` rather than listed, the same derivation `TheImpactComesBack` makes for a charger's own passive roll. |
| **Both ceilings apply to an improvised weapon: p.87 caps the Trait and p.108 caps the attack rank.** | `scenery_as_weapons`' own `ambiguity` says it in as many words — "whether the six-dice cap replaces Chapter 6's ceiling or sits beside it is not stated". Applying one alone would be choosing which page to ignore, and applying both is the only reading that never hands out more than either page allows. The two bite in different places, so neither is redundant: p.87 caps the rank before the printed die is added and p.108 caps the sum. |
| **p.74's throwing range is a limit on where a thrown object may be aimed, not a penalty on aiming further.** | The page says what a throw reaches — `accuracy_is_what_is_measured` — and prints nothing at all about throwing past it, so the two honest answers are to refuse the throw or to report the distance and let it fly. Refusing is the one that never resolves an attack under a rule the page does not print; the ledger line names the figure and the formula, so a caller can see how far it would have gone. It bites only where the object carries a **weight rank**, since that is the operand `rank_formula` subtracts: an object with a Structure instead has no printed distance at all, and the line says the reach is the GM's rather than reading one figure as the other. |

And one the engine **consumes** rather than makes, with a doc comment naming the entry: `gritty_fatal_damage`'s `interpretation` — a spent Resolve leaves you one point *above* the fatal threshold, which is what the worked example computes, against a printed word that says below. The ledger line quotes both.

## `Combatant`, and the one place a sheet is read

`CombatantFactory.From(sheet, rules, derived, play, kind)` is the only code in `play/` that touches a `CharacterSheet`. Everything after it works on immutable `Combatant` snapshots, which is what makes `Encounter.Step` pure and is checked from the other side by the byte-identical round-trip test.

**The caller supplies the `Kind`.** It is an argument and not something read off the sheet: the flag on a character is presentation, no rules code may see it, and the same sheet is a Villain in one game and a Foe in another. `Kind` is the only thing that decides whether Health is halved and whether Resolve is held.

**The caller supplies the `Side` too, and it is a separate field on purpose.** Nothing in Ch.3–5 says who is on whose side — p.73's ladder is about precedence, not teams — so `Combatant.Side` is a free-form name the caller chooses, and `OneSideIsDown`, `Over` and `AttackTheWeakest.IsEnemyOf` partition on it and on nothing else. Deriving it from `Kind` was a defect rather than a reading: it made p.73's fight between Heroes unendable (every combatant was on the Hero side, so no side could ever be down) and put a Villain's Minions on the same side as the Foe they were fighting. The factories default to `heroes` for a Hero and `villains` for everybody else, which is the arrangement every fight the book works through happens to have; `Kind` still decides tie order, Health and who holds Resolve.

**Only a Hero can hold Resolve, and the type is what says so** — the constructor is private and `Combatant.Hero` is the only factory that takes a pool, so a spend charged to anybody else is a throw rather than a silent draw on nothing. Ch.2 says it twice; the character engine computes the figure for everybody and it is noise on a Villain. Here it is not noise, it is unconstructible.

**Four fields on a `Combatant` are the caller's word and are not read off anything**: `Side` (above), `Size`, `Invisible` and the opening `Holding` that `Carrying` sets. Each is a fact Chapters 1–5 give this engine no way to derive, each defaults to the arrangement every figure here has been measured under — the book's own sides, the same size as everybody, and visible — and each is in the readings table above with the page that made it necessary. The one thing `CombatantFactory` *does* add for p.75 is `Powers`, the ids on the sheet whatever their rank, because a capability is a thing a sheet can answer for.

**A Foe's Health is halved upward.** p.75 says a Foe halves the result and never says which way an odd total goes; the Glossary's book-wide rule (p.7) pushes a half up, so a Health of 3 halves to 2 and not to 1. Both directions are computed in the test and the wrong one is required to be wrong.

## A campaign's table, and where it crosses

`TableRules.From(CampaignTable)` is the one seam between the two lists that name the same thirteen
switches. `engine/CampaignTable` is what a campaign stores and a character carries — the browser
writes it, an account's server relays it without parsing a word, the `.json` export copies it onto
the sheet — and no rules code over there reads a switch, because none of them is about what a
character costs. This is where they become something a fight can be resolved under.

**Switch by switch, and `GearLimitRank` crosses as a figure.** `CampaignTableNamesTests` already
held the two *lists* together by reading `TableRules.cs` as source; it now reads `From` the same way
and requires every setting to be assigned from the one with the same name. That catches the quieter
failure: a switch present on both sides and left out of the conversion compiles, passes the list
check, and is a house rule a GM turned on that every fight is resolved without — with the campaign
page saying it is on and the run's echo honestly reporting the table the encounter was built with,
which is off. A copy that reached the wrong field is caught too, because both sides are booleans.

**`TableRules.FirstDifference` names the setting two tables disagree about**, in `Switches` order.
The record's own equality would answer the question and would answer it with a bare `false`; a
fight refused because its sheets disagree has to be refused with the switch in the message, or
nobody can go and fix the sheet that is wrong. The rank is compared as a *figure* — `IsOn` answers
only whether one was set at all, so a table on 9 and a table on 12 would agree under it.

**Nothing in `play/` reads a `CharacterSheet.CampaignTable` itself.** `CombatantFactory` is still
the only code here that touches a sheet, and it does not look at the block: which table a fight is
under is a fact about the *scene*, decided once by the host out of every sheet it was handed, and an
`Encounter` is built with the answer. See [`mcp-and-headless.md`](mcp-and-headless.md) for how the
encounter server decides it and what it refuses.

## Policies are not rules

`IPolicy` says which intent a character would have chosen. That is a person's decision at a table and a guess anywhere else, which is why `IPolicy.Name` exists and why **every report built on a run has to print it beside the seed, the N and the table settings.** A balance figure is a figure about a particular way of playing; one quoted without its policy is a figure about nothing.

`AttackTheWeakest` is the one that ships: hit the enemy with the least Health left, with the best available attack Trait, and buy a reroll when the roll fell short by two successes or fewer. **What "available" means is derived, not listed** — p.75's table names the attacking Trait of every row, and the table's "Power" column means the combatant's own, which is the same derivation `ChooseDefence` makes on the other side of the roll. Four ids used to be typed into the policy, and a character built out of Energy Blast held their action for a whole fight while holding an obvious weapon. **The two is a judgement, not a rule** — the page puts no condition on the purchase at all — and a policy that rerolled everything or nothing would answer a different question from the one a balance run is asking.

`RunToEnd` takes a page limit, and **the limit is why it terminates rather than an argument that it would**: two combatants who cannot get through each other's defences would fight for ever, and a simulator that hangs is worse than one that reports a draw.

### The four styles, and the fifth that is not one

A fight is run in a **style** — how freely a side reaches for its pool — composed with a **target selector**, which is an axis of its own because who a side swings at and how much it spends are not the same habit. `StylePolicy` is the base and each style is a subclass whose **doc comment lists every rule it uses**, because that list is the whole of what a rate measured under it is a rate about.

| Style | What it does |
|---|---|
| `mano_a_mano` | Never emits a purchase. The floor every other figure is read against. |
| `standard` | Seizes when out-Edged; answers a point spent against it on the previous page with a reroll. |
| `min_max` | Prices dice against the shortfall, rerolls where dice cannot reach, seizes when the order would move, leads a team attack between adjacent allies, and goes all-out only where the worst counterattack could not put it down. |
| `reckless` | All-out on every page, no point ever spent on staying alive. The upper bound. |

**`narrative` is refused by name and there is deliberately no fake one.** The owner's fifth style is the Villain acting befitting their character, with their Flaws coming up — and a seed cannot fake it: **nothing in `play/` makes a Flaw bite**, which is p.85's own position (the suppression spend it sells says the effect "never reaches the state"), and "befitting" is a judgement rather than a comparison. It is the live `take_turn` path with a model as the Villain. `StylePolicy.NarrativeIsNotSeeded` carries that sentence in one place, the server refuses the name with it, and `PLAY-POLICY.md` prints it — so nobody reads the absence as an oversight and nobody builds a stand-in.

**Every spend goes through `AfterRoll` and none through `Choose`**, and that is a decision with a cost. `RunToEnd` gives a policy one choice and one follow-up a turn, so a purchase returned from `Choose` *is* the turn: the character buys their place at the front of the order and swings at nobody. Buying afterwards costs nothing and reaches every purchase Chapters 4 and 5 price after the roll — p.84 says both of the commonest are decided with the dice on the table — and no purchase in either chapter has to be made before one.

**Whose money pays is the kind of character and never the style.** Only a Hero holds Resolve, so an NPC's purchase is p.85's first Adversity spend with the same `ResolveSpend` named inside it. A group of Minions buys nothing: p.73 and p.77 refuse them four of the ten outright, and the refusals would be the whole of what a Minion policy produced.

**`mano_a_mano`'s claim is checked over a hundred fights and its control is `standard` on the same seeds.** "The ledger has no purchase in it" is satisfied perfectly by a scan that has stopped finding purchases, which is this repository's commonest guard fault; so the fixture requires the other style, on the same seeds and the same sheets, to produce lines the same scan finds.

### What a run observes, and the one thing it cannot observe

`RunObserved` walks the same loop as `RunToEnd` and records each exchange and each defeat, because **a win rate is not the whole of a balance question**: what a party has no answer for is a question about which attacks landed and which defences held, and a fight that ended 4–0 and a fight that ended 4–0 because one Power went through everybody are the same two numbers.

Everything in it is read off `ResolvedAttack` or off the difference between two immutable states, so a refusal, a halved pool or a capped rate moves the observation with it — an attack the rules refused is not an exchange at all, because every refusal in `ResolveAttack` returns without touching `LastAttack`. **An exchange is recorded per turn and not per step**, so a bought die and a reroll, which re-apply the attack already on the table, do not become a second attack.

**Two facts are not on the state and are read back off the ledger** — the Trait that answered an attack, and how much damage a particular attacker has done so far. `LedgerReading` is where both live, each anchored on the one line of `Encounter.Step` that writes it and throwing when that line moves. The count of exchanges the defending Trait could not be read for is **published in every report** as `defence_traits_unread` rather than swallowed: it is zero on every fight this engine resolves, and above zero the defence tables are short by that many rows.

**The one case the observation deliberately does not separate is p.80's Friendly Fire**, whose stray round is a second attack resolved inside the first and overwrites `LastAttack`. That setting is off in every default measurement, and this is where that is written down.

## Chapter 7's scenery, and the three Chapter 4 rules that needed it

**Three rules named a figure this engine had nowhere to look up, and `environment.json` prints all three.** p.75's cover wants a Structure, p.78's knockback wants an object "tougher than they are", p.74's throw wants "the object's weight rank" — and each was the caller's word, or nothing at all, for as long as Chapter 7 was loaded and applied by nothing. `Encounter.Scenery` reads the three object tables: p.107's Smashing table rates a **material** (22 names), p.108's Scenery table rates a **thing** (20), and p.108's Massive Objects table replaces the rating with a **weight rank** for what is too big to have a useful one (16).

| Rule | What it takes | What Chapter 7 gives it |
|---|---|---|
| p.75's cover | `Attack.CoverScenery` | the row's Structure, cited on a line of its own beside p.75's two |
| p.78's knockback | `SpendResolve.SolidObject` | the Structure the target's passive defence is compared with, and half the blow again where it does not exceed it |
| p.108's improvised weapon | `Attack.Item`, where Chapter 6 prints no weapon of that name | `close_combat_bonus_dice` or `thrown_attack_bonus_dice`, and a ceiling of the row's own rank plus `cap_bonus_dice` |
| p.74's throw | the same `Attack.Item`, on p.75's Ranged Weapon row | the **weight rank** `rank_formula` subtracts — the operand Chapters 3–5 never had |

**The bare figure never went away, and that is the point rather than a compatibility hedge.** p.107 lets the GM move a Structure by as much as four dice for how thick or how rotten a thing is, and its own second worked example does exactly that to a telephone pole; no table prints every object in a city. So `Attack.CoverStructure` still takes a number, and naming a row is the other way of saying the same thing — with the ledger citing the page the figure came off instead of recording it as somebody's say-so.

**Every refusal here is a refusal rather than an invented figure**, which is the whole reason the tables are worth reading: a name no page rates, a phrase two rows tie on, and a Massive Objects row where a Structure is wanted are each answered with nothing rolled and nothing spent. The alternative — a plausible number and a citation — is the class of line this ledger exists to prevent.

**Two of p.108's own clauses are applied and one is named.** `massive_objects`' `always_breaks_apart_after` is "the first shot", and there is somewhere for that to land: `Combatant.Dropped` already exists for p.76's page turn, so a thrown freight train leaves its thrower empty-handed and an attack naming it again is refused by the guard that already refuses an attack made with what its actor does not hold. `scenery_as_weapons`' two dice a page of wear is **not** applied, because `degradation_applies_to` scopes it to "an everyday object used as a weapon by a super strong character" and the entry's own `ambiguity` says the page never gives that a rank — a threshold this engine invented would be one nobody could argue with.

**`vehicular_gear_limit` is not read, and it does not need to be.** Ch.6 p.94's entry says a vehicle is mundane gear under the ordinary Gear Limit, and it lives in `data/rules/vehicles.json` — the *character* rules, which `play/` may not read and `NothingInTheApplicationNamesAPlayRulesFile`'s mirror image keeps it out of. What a fight applies to a named vehicle is p.87's ceiling, which is the same figure by another route: a Humvee is a row of the Scenery table, an attack naming it is an attack naming an item, and `Encounter.GearLimited` caps it exactly as it caps a sword. **What is not modelled is the vehicle itself** — a `Combatant` has no vehicle, nothing in a fight is driving one, and a vehicle's own four ranks are a character-side calculation `PROGRESS.md` item 32 puts on the sheet. A Humvee here is a heavy object, and the ledger never calls it anything else.

## p.87's Gear Limit, and the item it bites on

**Two chapters, and both are read.** p.80 offers the table the switch and names the figure — `TableRules.GearLimit` is where "the entry's default, or the rank this table raised it to" is decided — and p.87 is the detail it points at: what the ceiling covers, what a Weapon Bonus is added to, and the three tables that say what each weapon is worth. Neither half is any use alone, which is why both switches sat unapplied until `data/rules/play/equipment.json` arrived. See [`play-rules.md`](play-rules.md) for how that file was extracted and why its rows are derived from the corpus rather than transcribed a second time.

**`Encounter.GearLimited` is the whole of it**, and it runs on an attack that names an `Item` the actor holds: the Trait's rank is capped at the limit in force, and the weapon's bonus dice are added to what is left. The ledger line names the entry, the limit, the rank before and after, and which printed weapon the item was matched to — or says the bonus is the GM's, where Chapter 6 prints no such weapon.

**It runs before p.75's cover refusal, and that ordering is load-bearing.** Two rules compare an attack rank with an obstacle's Structure — p.75's attack through cover and p.78's guard on going all-out — and the rank an item-backed attack brings to bear is the capped one. So p.76's two refusals about the object (the contested-item deadlock, and an item the actor is not holding) and the cap itself all come before the shot is considered, and `UseTheItem` still comes after every refusal, because `HeldItem.Used` is a state change and a refusal must not buy one.

**Which attacks it reaches, what it does to a Power, and what p.87's own exception is** are three readings and are in the table above with the sentences they come from.

**Naming an item also answers p.79's Close Range rule, and that junction was a disagreement between two slices.** `Attack.CloseRangeOnly` exists because "a fight here has no equipment in it, so nothing can tell a pistol from a throwing knife but the person running the fight" — which was true when it was written and stopped being true here. `gritty_close_range` is `ignored_for` "ordinary thrown weapons"; `weapon_bonus` says a ranged weapon reaches Distant Range unless it carries one of `ranged_reach_exceptions`; and every weapons row carries its printed features. So an attack made with an item Chapter 6 prints as `Thrown` is exempt whether or not the flag was set, and until now such a caller had their target docked two dice for a weapon the page exempts by name. **The feature is looked up in the two entries rather than typed**, because the other reach exception moves the reach the other way: `Line of Sight` is the sniper's rifle, which is not a short-range weapon and must not be exempted beside the knife — a pair that stops naming exactly one feature between them throws. The declaration still comes first and still covers what a printed row cannot: an item no table carries, and a weapon being used in a way its row does not describe.

**The cap is applied on the attacking side only, and the other side is named rather than left silent.** Chapter 6 prices a weapon in both directions — p.88 adds its bonus to "your Agility or Martial Arts rank when defending yourself against close combat attacks", and p.87 caps "the maximum Trait rank you can apply when using mundane equipment", which is a sentence about applying a Trait rather than about attacking with one. So a defender holding a printed melee weapon has a bonus this engine does not lend them and a ceiling it does not put on them. `Encounter.ArmedDefence` writes that on the ledger whenever a close combat attack is answered by somebody holding one, because **an unapplied half nobody can see is the failure this ledger exists to prevent** — the attack side of the same rule is applied, so a reader has every reason to assume the defence side was too. It is named rather than applied because p.87 prints its exception for a "defense rank" in the same breath as an attack rank, and the entry's own `ambiguity` says the page never settles who takes it: capping alone would take dice off a defender the page offers a way out to, and lending the bonus alone would hand out dice the ceiling is meant to bound. Both halves are one decision and it is the wielder's.

**Mundane armour — the other half of p.87's "usually armor and weapons" — is unreached rather than declined, and this sentence is the whole of the answer.** A `Combatant` carries no gear: `SelectedGear` is a field on the character sheet and `CombatantFactory` never reads it, so **no defence in a fight here is item-backed**, and the Armor *Power* is a Power rather than mundane equipment — p.87 caps neither. There is nothing to cap on that side until a fight can be opened with armour on somebody, and inventing the flag to hang it off would be inventing a fact no sheet backs, which is the argument that kept the whole rule unapplied before Chapter 6 arrived.

**The claim that the ordering is load-bearing is now a check.** It was not: reverting p.75's cover test to the bare Trait rank, reverting p.78's all-out guard to it, and handing `ResolvedAttack.AttackRank` the bare rank were three separate mutations and **not one of them turned the suite red**, so the argument the whole slice turns on — "it is the rank and not the pool" — was carrying nothing an instrument could see. `TheCappedRankIsWhatACoversStructureAndP78sGuardCompare` drives all three where the two readings disagree: a 10d Might under the 6d limit swinging a +3d axe brings 9d to bear, every obstacle in it is set at exactly 9, and the controls are the same weapon against an 8 and the same swing with no weapon at all.

**The fixtures drive both sides of every threshold.** A 10d Trait comes to bear as 6d and a 4d one comes to bear whole, because a cap that fired on every rank would be indistinguishable from one that fired on none; p.87's own worked example is replayed at 12d Might for the printed 8; a raised limit is driven through `CampaignTable` → `TableRules.From` → the cap and compared with the default answer rather than with a number written in the test; a Power-backed attack and a fist are driven on the same Trait and the same weapon, so the only difference between the answers is p.75's row; and an item Chapter 6 does not print is capped and gets nothing, with `a battle axe` beside it as the control that the lookup can still find a weapon. The defence line is driven on both sides of its own condition too — empty hands and an unprinted object each write nothing — and the defender's pool is compared with the same fight's unarmed one, so a line that had started moving a figure fails beside the line that says it does not.
